# ADR 3.1.0002 — Minimal employee record attributes

> ADRs are written and consumed in **English**, even when the rest of the project docs are in Portuguese. This keeps them grep-friendly and reusable across projects.

## Status

`accepted`

## Context

The domain doc [`docs/domain/staff/workforce.md`](../domain/staff/workforce.md) §3.1 explicitly
delegates to the Stage 3.1 concept the **minimal cadastral attributes** of the employee record
("nome, contato, o que identifica o registro dentro da unidade") — no ratified source enumerates
them. Forces:

- Every v1 feature that touches the record needs a **display name**: the roster, the schedule
  calendar mini-cards (overview §3 — hub), the copy-to-unit flow.
- No v1 feature consumes **contact data** from staff: the login invite (Stage 3.5) takes the
  e-mail at link time and stores it in identity's `User`; schedule-publication e-mails (Step 4)
  go to the login e-mail. Storing a second e-mail in staff would duplicate identity's data and
  invite drift.
- Free-text personal data is persisted **verbatim** — no silent normalization
  ([ADR 2.3.0005](./2_3_0005-names-persisted-verbatim.md)).
- The record is per unit; the person (User) is global (workforce §3.1, kickoff #2). Two distinct
  people with the same name in the same unit is a legitimate real-world case.

## Decision

The employee record's cadastral minimum in v1 is:

- **`EmployeeId`** (opaque typed id) — the only identity of the record. Generated by
  application/infra, treated as opaque by the domain (same pattern as identity, Stage 2.1).
- **`name`** — free-text display name; **non-empty** is the only structural rule, where
  non-empty means **at least one non-whitespace character** (whitespace-only is rejected — the
  `.strip()` **validation predicate** of the identity precedent, which does NOT alter the
  stored value); persisted **verbatim** (ADR 2.3.0005); **NOT unique** within the unit or the
  tenant.

No contact fields (phone, e-mail), documents, admission date or notes exist in v1. Adding any of
them later is an **additive evolution** (new optional column/field) that does not remake the
record's shape.

The record also carries `tenant_id`/`unit_id` (structural, from workforce §3.1 invariants), the
workload profile, the optional shift preference and the unavailability periods — those are fixed
by the workforce doc and by ADRs [3.1.0001](./3_1_0001-workforce-gate-modeling-decisions.md),
3.1.0003 and 3.1.0004, not by this one. The reference to the job function exists (workforce
§3.7) but its **cardinality is decided by the sponsor fork tracked in the Stage 3.1 concept**,
not here.

## Alternatives considered

### Alternative A — Rich cadastre (contact, document, admission date)
- **Description:** model phone/e-mail/CPF/admission date on the record from day one.
- **Pros:** one form captures everything; no later migration.
- **Cons:** no v1 feature reads any of it; a staff-side e-mail duplicates identity's and drifts;
  personal data stored without a consumer is LGPD surface for nothing (overview §6 — LGPD básica).
- **Why rejected:** every field is additive later; storing unread personal data is cost and risk
  with zero v1 value.

### Alternative B — Name unique within the unit
- **Description:** enforce uniqueness of `name` per unit (like job-function names per tenant).
- **Pros:** avoids ambiguous rosters.
- **Cons:** homonyms are legitimate (two "João Silva" in one kitchen); uniqueness would block a
  real cadastre or force the manager to mangle names. Job-function names are a controlled
  vocabulary (uniqueness is meaningful there); person names are not.
- **Why rejected:** identity of the record is `EmployeeId`; the UI can disambiguate visually.

### Alternative C — Reuse identity's User name as the record's name
- **Description:** no name in staff; resolve the display name through the linked User.
- **Pros:** single source for the name.
- **Cons:** login is optional (overview §3) — most records have no User; would invert the
  Stage 3.5 dependency and couple the BCs for a basic display need.
- **Why rejected:** person ≠ record (workforce §3.1); the record must stand alone.

### Do nothing / status quo
Not viable: the domain doc marks the attribute set as a lacuna the Stage 3.1 concept **must**
fix before the entities are modeled.

## Consequences

### Positive
- Smallest possible LGPD surface in staff v1; no duplicated contact data to drift.
- Homonyms never block a cadastre; `EmployeeId` is the only identity, as DDD prescribes.
- Any future field is additive — no shape remake.

### Negative
- Rosters with homonyms need visual disambiguation (function/profile shown next to the name).
- If a future feature needs employee contact without a login, a field must be added then
  (accepted: additive).

### Neutral / trade-offs accepted
- The copy-to-unit flow (Stage 3.2) duplicates only this minimal set — copies stay cheap.

## Implementation notes

- Lands in Stage 3.1: `features/staff/domain/entities/employee.py` (non-empty check raising the
  staff name exception; no normalization).
- Persistence (Stage 3.3) must NOT add a unique index over `name`.
