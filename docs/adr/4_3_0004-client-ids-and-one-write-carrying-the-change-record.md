# ADR 4.3.0004 — Client ids and one write carrying the change record

> ADRs are written and consumed in **English**, even when the rest of the project docs are in Portuguese.

## Status

`accepted` — 2026-11-01.

## Context

A per-allocation violation key (ADR 4.2.0002 Decision 5) contains assignment ids. If the server
generated the ids of entities created in a batch, `evaluate` and `publish` would generate different
ids for the same batch and an acceptance returned by `evaluate` would never match in `publish`.
Separately, Stage 4.4 must record "who changed what and when" for every mutation, and ADR 2.6.0002
§5 (check_layout rule 10) requires any use case writing twice to do it inside a unit of work — a
port scheduling does not have.

## Decision

1. **Client ids.** `EnableBand.band_id`, `DeclareDemand.demand_id` and
   `AssignEmployee.assignment_id` come from the client (opaque strings, validated at the boundary,
   ADR 3.6.0002). Uniqueness is per (tenant, unit): ids already used, of the same type, in the
   loaded schedule or a neighbour → `IdentifierInUseError` before applying; used by another
   schedule of the unit → `save` refuses with the same error (law L-SC4). The schedule id itself is
   generated by the server (`IdGenerator`) on create.
2. **One write carrying the change.** `add(schedule, change)` and `save(schedule, expected_version,
   change)` receive a `ScheduleChange` — author (`AuthorizedScope.user_id`), `Clock.now()`,
   previous version, effective operations in order, acknowledged violations. The adapter persists
   state and trail atomically (law L-SC3). Create and publish write once; rule 10 needs no unit.

## Alternatives considered

### Alternative A — Server ids plus batch-local references
Rejected: the acceptance key would not match between evaluate and publish.

### Alternative B — A separate audit port written after the save
Rejected: two writes per use case → a unit of work port for scheduling (ADR 2.6.0002 §5), and a
window where the state is saved without its trail.

## Consequences

### Positive
- Acceptances are stable between evaluate and publish; the trail is never missing.
- No unit of work in scheduling.

### Negative
- Clients must generate good ids (UUID canonical format at the boundary — finding 4.5).
- The trail's storage shape is constrained to be writable in the same transaction (4.4).

### Neutral / trade-offs accepted
- N effective operations raise the version N times and are all listed, in order, in one
  `ScheduleChange`; whether 4.4 stores one row per operation or per batch is its granularity gap
  (domain doc §6) — "every mutation generates an audit entry" (doc §3.5) holds either way.

## Implementation notes

The fake repository records each `ScheduleChange` next to the state for tests; 4.4 adds the real
adapter to the same law suite.
